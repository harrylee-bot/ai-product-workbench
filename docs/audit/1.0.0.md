## 产品范围

在线输入中文需求，结合授权知识生成需求文档和原型；文档在线阅读、编辑并下载 Word/PDF，原型通过固定版本链接分享和交互预览。默认交付“需求文档＋原型”，也保留单产物选择。

知识源为仓库的 `knowledge-vault/`、项目数据库和本地 `storage/`。源资产与生成知识没有同步到外部知识库。文档下载按登录后的项目权限验收；本次不增加文档的匿名公开分享。

### 不能直接替换的关键原因

1. **产物合同不同。** 当前 screens/nodes/tokens/assets/variables/states/actions/bindings/motions 同时支撑生成校验、流式 patch、手工编辑、导出和知识抽取。任意 React 无法无损反推这些稳定身份与业务语义。通用 React↔IR 双向转换成本高且会重新限制代码自由度，不作为推荐方案。
2. **代码执行边界不同。** Axhub 会在工程目录安装开发依赖、运行构建和开发服务器，Coding Agent 也需要文件/命令能力。必须按工作区隔离进程、目录、网络与密钥，设置 CPU/内存/磁盘/时限。仅 iframe 嵌入不能解决服务端执行问题，也不能把开发目录 URL 当发布版本。
3. **安全预览与创作工具存在结构冲突。** Axhub 编辑桥依赖 iframe DOM/运行时能力；工作台当前 CSP 是 `connect-src 'none'`、hash 脚本及无 same-origin sandbox。要通过独立 origin、明确消息协议、受控构建产物解决，不能假定增加 sandbox 后全部功能仍正常。
4. **生成完成不等于业务成功。** 需要经过构建、页面/交互检查、知识引用校验、源码和构建快照提交后才能 ready。Axhub 部分生成提示词跳过浏览器验收，而客户端开发规范要求验收，提示词存在不一致；必须由工作台定义统一验收门槛。
5. **版本与语义不能靠目录约定替代。** Git 回退有价值，但没有天然保证生成任务、评论、源码、构建和知识定稿属于同一不可变版本。代码重构还可能使 DOM locator 失效，应有稳定页面 ID 和失效标注迁移机制。
6. **长期维护能力尚有缺口。** 根许可证为 Apache-2.0，可依法使用/修改/分发；仍须保留许可和归属、核查第三方依赖。`vendor` 的 agent-surface、export-core、tiptap、excalidraw 等部分只有 dist/scripts，不能据此断言禁止使用，但也不能承诺完全从源码重建和任意深度定制。本轮未做全依赖许可/漏洞审计。

安装的 ACP Codex provider 还默认采用 `agent-full-access` 并继承宿主环境。这进一步支持将其放入受控执行器的要求；提示词限制写入目录不能替代操作系统级隔离。

### 三种替换路线

| 路线 | 价值与代价 | 判断 |
| --- | --- | --- |
| 只把 Axhub 当另一个提示词/生成器，继续输出旧 IR | 业务改动相对少，但必须约束 Agent 输出旧合同，代码创作与编辑优势大幅受限；也不能直接调用其现有 React 流程完成 | 仅适合提示词/质量实验，不作为主要替换路线 |
| 新增源码型原型，Axhub 承担创作执行，工作台掌握任务/知识/版本/权限/交付 | 可逐步替换新原型生成路径，保留现有业务资产；需要任务桥、合同、构建/预览和知识语义适配 | **推荐，先对比验证再灰度** |
| 整套 Axhub 管理端直接代替当前原型子系统 | 演示嵌入快；生产需重做多租户、隔离、统一身份、状态一致性及维护；既有 API/历史数据/权限语义会退化 | 当前不建议；不能以 iframe 验证通过作为上线依据 |

推荐边界：`工作台 Run/授权知识/PRD → 执行适配器 → 隔离 Axhub＋ACP 工作区 → 构建与验收 → 不可变源码/静态包 → 工作台版本、分享、导出和定稿`。DeerFlow 与 ACP 不同时拥有业务任务终态与重试权；前者可继续统筹 PRD/知识，后者只负责受委派的代码执行。若后续改成 DeerFlow 直接写 Axhub 工程，也需另验兼容性，不能混同已完成接入。

建议源码产物清单至少包含：独立 protocol/schemaVersion、documentId、稳定 pageId/route、sourcePrdVersionId、knowledgeReleaseId/citations、源文件包和锁文件 hash、生成工具版本、构建包 hash/入口、资源清单、截图、页面/状态/交互摘要、批注所属版本。数据库存索引与不可变对象引用；大源码/资源包存 storage/对象存储。协议名称仅为设计建议，本轮未创建或修改正式 schema。

创作时使用可回收的隔离工程；发布和匿名预览只使用固定构建包。管理端、生成代码、工作台应具备清晰的 origin 和凭据边界；即使使用反向代理，也须验证本机放行判断、转发头与直连端口，不能只靠隐藏入口。

### 迁移、验收和退出条件

先保持历史 `workbench.prototype.v1` 的查看、编辑、分享、导出和知识读取，新建原型按项目 feature flag 选择源码路径。旧原型确需迁移时，可尝试既有 React 导出的一次性转换，生成新产物并保存来源；不得承诺无损回写旧 IR，不修改历史发布链接或清理已发布知识。回退时关闭新建源码路径即可，已经发布的源码产物仍保留其独立渲染能力。

| 阶段 | 交付与通过条件 | 失败时的决策 |
| --- | --- | --- |
| A：质量与生命周期试验 | 3 类脱敏业务样例（筛选/表单、多页流程、共享组件局部修改）；同输入、相近预算，并行对比当前路径与 Axhub；完成生成→修改→冻结→回看、取消和重启恢复 | 若质量/修改成功率无收益，停止替换；可只复用标注/交付思路 |
| B：受控开发接入 | 薄任务桥＋源码合同＋构建快照＋开发环境预览/保存；明确真实引用、PRD 来源和 ready 提交边界 | 若必须靠脆弱 UI 自动化或频繁 fork 才可驱动，重新评估维护收益 |
| C：项目灰度 | 两用户两项目的全部入口隔离；分享撤销/成员退出/项目停用有效；限额、依赖失败、取消、重启、乱序事件、并发修改均不污染已发布版本 | 任一越权、密钥暴露、版本错绑或不可回滚问题阻止默认切换 |
| D：替换默认新建路径 | 全链路“授权知识→PRD＋原型→批注修改→保存→分享→撤销→导出→定稿→后续引用”通过；旧 IR 回归通过；容量和单位成本可接受 | 保留旧生成器；仅在已通过的项目/场景启用 |

建议在实施前锁定一组可量化门槛：至少 10 个代表场景各运行 3 次，记录首轮可用率、最终业务验收率、非目标页面回归率、人工修改轮次、首个预览/最终完成 P50/P95、模型 token/调用费用和执行器成本；模型、设计输入与预算必须可比。单次 smoke 只证明链路可用。新路径最终验收率不应低于基线，视觉与复杂交互收益需要用户验收；安全隔离、分享撤销、历史兼容及固定版本一致性为必须全部通过项。实际成本门槛和目标并发需在试验后按业务负载确定。

导出验收分别覆盖 HTML 静态运行、源码重建、Figma 图层/Make、Axure runtime/可编辑元素。新增产物不等于所有格式必须首期齐套；若要求与旧编辑器和全部出口完全等价，应单列范围，不能以“已替换生成能力”隐含承诺。

## 服务器稳定性与发布方案

服务器构建事故的直接原因是生产 Docker 主机执行未经资源约束的并行 Compose 构建。多个 `npm ci` 与 Chromium、LibreOffice、字体和 Python 依赖安装，和在线业务争用内存、磁盘与 IO。原受限构建脚本的保护不能约束绕过入口的命令。

GitHub 官方计费文档确认自托管运行器不消耗托管运行分钟；私有仓库使用 `ubuntu-latest` 有免费分钟额度。仓库现有的 `workbench-typecheck-16g` 经现场确认装在生产主机，禁止作为构建替代。已启用独立本机 Colima Linux ARM64 环境：4 CPU、8 GiB 内存、24 GiB 系统盘、64 GiB Docker 数据盘，不挂载个人目录、不转发 SSH agent、不开放应用端口。生产发布镜像必须显式为 `linux/amd64`，并实际运行兼容性检查。构建与部署分离，网站仍部署在生产服务器，本机关闭不影响线上服务。

自托管计算不会消除 GitHub 的制品/缓存存储限额。现场只读清单：513 个制品合计约 279 MiB，缓存约 9.99 GiB；当前工作流已取消云端构建缓存和重复自动制品，保留必要测试与签名证据并设置较短保存期。此方案不更改仓库私有属性，也不启用付费额度。

本版本采用以下完整发布流程：

1. **外部构建**：生产机不执行构建。GitHub Actions 对固定 main SHA 构建全部 10 个镜像，保留固定基础镜像、构建来源、SBOM、HIGH/CRITICAL 漏洞阻断和 Cosign 签名。扫描 Action 使用可解析的固定提交。推送后仅清理该临时 runner 的专用 builder 缓存，直接从镜像仓库生成 SBOM 和扫描，避免本地 Docker 导出副本耗尽 runner 磁盘。
2. **技术验收**：同 SHA 的完整 CI、真实 PostgreSQL 与浏览器、部署合同均通过后才签发发布包。项目所有者明确授权取代旧组织审批链，不伪造组织签署或跳过技术检查。
3. **部署预检**：校验签名、源码文件摘要、镜像标签和公开构建配置。检查 Docker 实际存储盘与备份盘容量，拉取前至少 20 GiB、拉取后至少 6 GiB；检查可用内存、主机部署锁和全部镜像可用性。
4. **备份与切换**：受控目录保存 Compose、旧镜像 ID、运行配置和已验证数据库归档；停止队列参与者，再迁移，按 Preview、Runtime、API/Worker/Web/知识站、网关顺序逐服务启动。只用不可变镜像和 `--no-build --no-deps`，设置 CPU、内存及进程数上限。
5. **失败恢复**：普通部署异常恢复已有应用镜像，保留恢复材料；数据库不自动反向迁移。执行入口应独立于 SSH 会话存活，中断后核查私有结果和服务健康，不能把断线当成功。主机故障或强制终止需要按保留材料恢复。
6. **验收与清理**：验证实际模型、知识引用、文档下载、原型分享和撤销后，再按引用关系删除确认废弃的镜像、缓存和目录；不执行 Docker 全量 prune，不删除活跃配置、业务数据或本版必要恢复材料。

Caddy 已配置 Docker 启动顺序及失败后 5 秒重试，修复 Docker 网桥未就绪导致永久退出的问题。系统单元校验通过，修改未中断需求池。
