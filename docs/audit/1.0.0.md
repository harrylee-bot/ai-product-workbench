## 产品范围

在线输入中文需求，结合授权知识生成需求文档和原型；文档在线阅读、编辑并下载 Word/PDF，原型通过固定版本链接分享和交互预览。默认交付“需求文档＋原型”，也保留单产物选择。

知识源为仓库的 `knowledge-vault/`、项目数据库和本地 `storage/`。源资产与生成知识没有同步到外部知识库。文档下载按登录后的项目权限验收；本次不增加文档的匿名公开分享。

## 构建事故根因与修复门禁（2026-10-09）

本次服务器失去 SSH、HTTP 和 HTTPS 响应的直接原因已确认：恢复缺失服务时绕过了受限构建入口，在生产 Docker 主机直接执行了 Compose 构建。该命令没有使用 `deploy/workbench-build.sh` 的主机锁、BuildKit cgroup 限额、单步并发和 MemAvailable 检查。

放大因素如下：

- Compose 同时构建多个服务；各服务独立执行 `npm ci`，导出 Worker 还安装 Chromium、LibreOffice、中文字体、Python 运行时和文档依赖。
- 导出镜像单层安装约 391 MB 系统包，峰值还包括解包、字体缓存、临时层和 Python wheel；失败构建会继续占用 BuildKit 缓存与 Docker 存储。
- 在线验证栈本身包含 ClamAV、Docling、数据库、Runtime、API 和 File Worker；部分服务没有 `mem_limit/cpus/pids_limit`，构建与运行服务共享宿主 RAM、CPU、磁盘和 IO。

因此问题不是“再把构建并发调小”就能根治，而是生产机同时承担业务机和构建机职责。永久修复方案是：生产只接受签名的 immutable image digest，由 CI 或独立构建机逐镜像构建并推送；`server-deploy.sh` 只执行签名清单校验、拉取、健康检查和可回滚切换。生产环境禁止裸 `docker compose build`、`docker compose up --build` 和 `docker system prune`。

只有临时验证且具备足够隔离时才允许同机构建，并且只能经过 `deploy/workbench-build.sh`：主机锁、BuildKit `max-parallelism=1`、单服务构建、明确内存/CPU/Swap 上限、运行中内存与磁盘监控、低于保留阈值主动中止。构建预算必须从实际主机总内存扣除在线服务峰值和至少 3 GiB 系统余量后计算；不足时 fail closed。导出 Worker 应迁移到预构建的 Chromium/LibreOffice 基础镜像，避免每次在业务机解包系统依赖。

服务器恢复后，执行顺序固定为：通过控制台检查 OOM/PSI/磁盘与残留 BuildKit → 停止残留构建但保留当前服务和回滚材料 → 仅拉取并校验 1.0.0 镜像 → 分阶段恢复服务 → 真实业务验收 → 生成引用图后再清理过期缓存和未引用镜像。现有受限构建脚本的 16 项单元测试已通过；本次事故说明入口保护还必须落实到生产权限和发布流程中。
