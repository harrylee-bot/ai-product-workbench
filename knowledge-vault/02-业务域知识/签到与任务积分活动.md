# 签到与任务积分活动

本页是签到、打卡、领积分和连续任务活动的现行业务规则。生成 PRD 或原型时，应同时读取活动发布、权益资损、报表治理和高保真原型框架。

## 业务定位

签到活动通过“用户完成一次可验证行为，系统记录参与结果并发放积分或权益”形成运营闭环。它不是单个签到按钮，至少包含后台配置、前台参与、资格与次数校验、奖励发放、失败补偿和数据复盘。

## 核心对象

| 对象 | 关键字段 |
| --- | --- |
| 签到活动 | 活动名称、活动时间、时区、用户范围、活动状态、登录方式。 |
| 签到规则 | 自然日口径、每日次数上限、连续/累计规则、补签规则、任务条件。 |
| 奖励规则 | 奖励类型、单次奖励值、每日额度、总额度、发放上限、有效期。 |
| 签到记录 | 用户标识、业务日期、签到时间、规则版本、幂等键、参与结果。 |
| 积分账本 | 变动值、变动前后余额、来源活动、关联签到记录、入账状态。 |
| 补偿任务 | 失败原因、重试次数、下次重试时间、处理状态、人工处理记录。 |

## 默认产品规则

- 未明确说明时，按北京时间自然日计算，每个用户每日成功签到一次；跨日后重新获得签到资格。
- 签到幂等键至少包含活动、用户和业务日期。重复点击不能重复记账或重复发放，只返回已有结果。
- 单次积分值、每日额度和活动总额度必须可配置。展示用示例值可以作为产品默认值，但真实预算、成本和库存必须由运营发布前确认。
- 连续签到、累计签到、补签和满值兑奖默认关闭；需求明确启用时，必须补中断、清零、跨周期和历史记录规则。
- 积分发放与签到记录必须可追溯。签到成功但发放失败时，记录进入“补偿中”，不能直接显示为完全成功。
- 活动开始、结束、下线、无资格、未登录、今日已完成、额度不足和系统异常都必须有明确前台状态。
- 修改已发布规则时必须生成新版本，说明对当天资格、连续天数、历史记录和报表口径的影响。

## 主流程

```text
运营配置活动、签到规则和积分额度
  → 预览并提交审核
  → 发布上线
  → 用户进入活动并完成登录/资格校验
  → 校验活动状态、自然日次数和奖励额度
  → 写入签到记录并发放积分
  → 成功反馈，或进入补偿队列
  → 报表统计与异常治理
```

## 状态与异常

| 状态 | 产品处理 |
| --- | --- |
| 未开始/已结束/已下线 | 主按钮不可参与，展示对应原因和活动时间。 |
| 未登录 | 引导登录，登录后返回活动上下文。 |
| 无资格 | 展示不可参与原因，不暴露内部人群规则。 |
| 可签到 | 展示本次奖励、今日进度和可执行主按钮。 |
| 今日已签到 | 展示签到时间、到账结果和下一次可参与时间。 |
| 发放补偿中 | 展示记录已受理、预计处理状态和记录入口，禁止重复发放。 |
| 额度不足/系统失败 | 阻止新增发放，记录失败原因，支持自动重试和人工处理。 |

## 数据与报表

- 核心指标：访问人数、签到人数、签到次数、签到成功率、积分应发/实发、失败数、补偿中、重复请求拦截数、额度消耗。
- 筛选维度：活动、日期、区域、渠道、用户范围、签到状态、发放状态、补偿状态。
- 明细至少展示脱敏用户标识、业务日期、签到时间、奖励值、发放状态、失败原因和补偿结果。
- 同一指标必须统一自然日、去重用户、测试活动和数据延迟口径；导出结果必须与当前筛选一致并留审计日志。

## PRD 重点

- 写明自然日与时区、每日次数、幂等键、连续/累计规则和规则变更影响。
- 写明积分额度、发放账本、失败补偿、人工处理、回滚和对账。
- 产品流程图和产品架构图必须覆盖后台、前台、规则校验、积分账本、补偿队列和报表。
- 验收必须覆盖重复点击、跨日、未登录、无资格、额度不足、发放超时、补偿成功和报表一致性。

## 原型重点

- 后台必须画活动基础设置、签到规则、积分/额度、展示素材、异常话术、预览审核和数据报表。
- 前台必须画首次进入、可签到、成功、今日已完成、无资格、未登录和补偿中状态。
