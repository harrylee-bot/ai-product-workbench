# Agent任务分类与补全规则

Agent 在生成 PRD、产品状态或原型前，必须先判断本轮需求属于哪一种执行模式。分类结果会决定知识调用顺序、原型一致性策略和是否需要追问用户。

## 三类执行模式

| 模式 | 识别信号 | 知识调用 | 输出原则 |
| --- | --- | --- | --- |
| 既有对话增量 | 用户说“新增、优化、调整、支持、补充”；需求指向已有活动、模板、素材、奖品、报表、页面，或当前对话里已有 PRD/原型/产品状态。 | 当前 ProductDesignState/PRD/Prototype 优先，再读 [[03-产品进化规划/历史业务增量规则|历史业务增量规则]]、对应业务域、[[05-原型设计规范/历史业务增量原型规则|历史业务增量原型规则]]、[[06-历史案例库/案例复用索引|案例复用索引]]。 | 不重构历史主流程，原型必须延续原导航、布局、字段分组、状态表达和交互习惯；新增内容只放在最贴近的历史位置。 |
| 全新功能 | 用户提出新模块、新工作台、新 AI 能力、新闭环、新角色或跨模块能力；当前对话没有可继承的历史页面或产物。 | 先读 [[01-产品架构/产品能力地图|产品能力地图]]、[[03-产品进化规划/新产品创新规则|新产品创新规则]]、[[05-原型设计规范/前后台页面框架|前后台页面框架]]，再补业务域和案例。 | 可以重组或重构页面框架，但必须落回产品能力层，复用账号权限、审核发布、数据复盘、素材、奖品、活动配置等平台能力。 |
| 一句话需求补全 | 用户只给一句简短目标，例如“做一个抽奖活动”“加一个 AI 营销助手”“优化素材库”；缺少角色、流程、字段或验收细节。 | 先读 [[01-产品架构/README|产品架构]]、[[02-业务域知识/README|业务域知识]]、[[06-历史案例库/案例复用索引|案例复用索引]]，再按任务类型读取 PRD 或原型规范。 | 不因信息少就直接停止；可根据产品架构和历史知识补全常规字段、流程、状态、异常和验收，并把补全内容标为 assumptions。高风险事实才追问。 |

## 判断流程

1. 先看运行时上下文：当前对话或内部上下文是否已有 ProductDesignState、PRD、Prototype、历史消息或附件。
2. 如果存在可继承产物，默认按“既有对话增量”处理，除非用户明确要求全新重构。
3. 如果没有可继承产物，但需求落在现有业务域，按“一句话需求补全”或“全新功能”处理。
4. 如果需求改变多个能力层、创造新对象或新闭环，按“全新功能”处理。
5. 如果无法判断业务域、目标用户、上线风险或资损边界，才返回 ask_clarification。

## 一句话需求补全边界

Agent 可以补全：

- 默认角色和权限范围。
- 常见后台配置页、前台参与页、预览审核页、报表页。
- 字段、状态、校验、空态、失败态、无权限态。
- 常规验收项、数据口径和风险清单。
- 与历史案例相似的流程和页面框架。

Agent 不能臆造：

- 真实活动预算、奖品成本、概率、库存和资损阈值。
- 真实接口地址、密钥、生产账号和内部运维信息。
- 监管、财务或合同类硬性规则。
- 用户明确没有授权的历史数据迁移或线上发布动作。

## 原型一致性策略

| 场景 | 原型策略 |
| --- | --- |
| 既有对话增量 | 先复原历史主页面，再标出新增字段、按钮、状态或区块；必须提供修改前/修改后影响说明。 |
| 全新功能 | 使用 [[05-原型设计规范/前后台页面框架|前后台页面框架]] 生成完整闭环，可重新设计信息架构。 |
| 一句话需求补全 | 生成最小完整闭环：后台配置、前台展示、预览审核、数据反馈；同时列出 assumptions。 |

## Final Action建议字段

DeerFlow final action 可以额外携带这些字段，后端会把它们保存在 raw 中，便于后续审计和 UI 展示：

```json
{
  "requirementMode": "historical_extension | new_capability | one_sentence_completion",
  "knowledgeRefsUsed": ["01-产品架构/产品能力地图", "02-业务域知识/活动发布与模板配置"],
  "assumptions": ["默认沿用平台活动发布流程", "后台需要配置页和预览审核页"],
  "consistencyStrategy": "历史增量沿用原导航和字段分组，只新增奖品核销状态"
}
```
